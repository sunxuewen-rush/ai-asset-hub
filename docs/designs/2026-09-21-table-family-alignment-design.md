### 1.5 排序档位收敛（D0-8 · 名称 / 作者下线）

**裁定依据（三条，均为实证）**：

| # | 依据 | 实证 |
|---|------|------|
| 1 | **结构上建不了索引** | 事务内试 `CREATE INDEX … ON asset ((coalesce(nullif((select v.name …), ''), slug)))` ⇒ **ERROR: cannot use subquery in index expression**（立刻回滚 · 残留检查 0）。两档排序键在 `asset_version`（JSON 投影）与 `user` 表 ⇒ 落在 PG 索引定义域外，**asset 表上任何索引都救不了**；20 万行实测 **357 ms**（= 最新档基线的 ≈39×），加排序索引后仍 `Seq Scan + Sort` |
| 2 | **中文序本身就是错的** | 真库 `datcollate = en_US.utf8` 实测序：`MCP → Z → b → 中文 → 技能 → 资产 → 阿`（**码点序**，非拼音序）⇒ 保留 = 用户点下去看见乱序；治好 = 一笔独立工程（物化拼音键） |
| 3 | **兄弟仓实测无此两档** | skillhub 排序值域 = `relevance / downloads / rating / newest`（`PostgresFullTextQueryService.java:85,89,166,168`）· UI 仅三个按钮（`web/src/pages/search.tsx:289-309`）· 全仓无 `pinyin` / 首字母排序 ⇒ 其「按名称找」由**全文检索**承担，不靠「按名称排列」 |

**连带收益**：余下三档（最新 / 下载量 / 星标）的排序键**全在 `asset` 表列上** ⇒ §1.6 的三条索引达成**档位 100% 覆盖**，「点排序 ⇒ 全表排序」这条路径整体消失。

### 1.6 服务端排序索引（D0-6）

**形态 = 部分索引**（照兄弟仓 skillhub V28/V29 先例；谓词 `status='ACTIVE'` ⇒ 只索引门户读的集合）：

```sql
1. (updated_at DESC, id DESC)                      WHERE status = 'ACTIVE'   -- 最新（默认档）
2. (download_count DESC, updated_at DESC, id DESC) WHERE status = 'ACTIVE'   -- 下载量
3. (star_count DESC, updated_at DESC, id DESC)     WHERE status = 'ACTIVE'   -- 星标
```

`idx_asset_status` **保留不动**（部分索引谓词只匹配 `ACTIVE`，个人面读 `HIDDEN` / `ARCHIVED` 用不上它）⇒ 本轮净 **+3**。

**实测（2026-09-21 · 20 万行 · 独立模拟表 · 跑完 DROP · 残留检查 0）**：

| 查询 | 基线（无排序索引） | 加索引后 | 倍数 |
|------|------|---------|------|
| 门户 下载量档 | 8.454 ms | 0.036 ms | ≈235× |
| 门户 星标档 | 25.097 ms | 0.059 ms | ≈425× |
| 门户 最新档（默认 · 最高频） | 9.177 ms | 0.035 ms | ≈262× |
| 深翻页 `OFFSET 1000` | 9.239 ms | 0.670 ms | ≈14× |
| `SELECT count(*)`（每次请求都发） | 7.270 ms | 7.936 ms | **不受益** |

**索引构建耗时实测（v1.9 新增 · 同 20 万行 · 真库内单事务跑完 `ROLLBACK` · 残留检查 0）**：

| 动作 | 耗时 | 索引尺寸 |
|------|------|:--:|
| 建 `newest` 索引 | 47.113 ms | 7,336 kB |
| 建 `downloads` 索引 | 41.706 ms | 8,976 kB |
| 建 `stars` 索引 | 40.636 ms | 8,976 kB |
| **三条合计 = 迁移写阻塞窗口** | **≈ 0.13 s** | — |

（对照：同表 20 万行 `INSERT` = 335.953 ms + `ANALYZE` = 37.722 ms；表 25 MB ⇒ 建索引开销 ≈ 同量级一次全表写。阈值讨论见 B6 / R5）

**现状无感（正证）**：真库 31 资产 / 37 版本 ⇒ `name` 档 **0.139 ms** · `newest` 档 **0.052 ms**（`EXPLAIN ANALYZE` 实测）⇒ 本轮做索引是**为量级预留**，不是修当下故障。

**已知边界（登记，不在本轮解决）**：

| # | 边界 | 说明 |
|---|------|------|
| B1 | **索引只覆盖固有方向（`desc`）** | `dir` 只作用于主排序列，tiebreaker 恒 `desc`（`service.ts:71-79`）⇒ `?dir=asc` **不是**索引序的简单反排 ⇒ 不享索引（低频路径：需点同一列头两次）；不为 asc 另建一条（索引数翻倍 = 写放大翻倍） |

### 2.3 列定义 `meta` 约定

列级 UI 约定走 `columnDef.meta`（tanstack 原生字段）。**类型实证**（2026-09-21 探针，见 **§13** 问题清单 F-1 —— **v1.3 订正**：原写「§11」有误，本件 §11 = 线框图）：

- `LegacyColumnDef<TData, TValue>['meta']` 的解析类型 = `ColumnMeta<LegacyFeatures, TData, TValue> | undefined`（**空接口**）⇒ 写自定义键**编译通过**（无 excess property 报错），读自定义键需一次**本地断言**。
- 故：件内自定义 `ColumnUiMeta` 类型 + 单点 `as ColumnUiMeta | undefined` 读取，**不 import `@tanstack/table-core`**（它是 `@tanstack/react-table` 的传递依赖，直接 import 即隐藏依赖 —— 沿用本仓既有纪律）。

```ts
/** 列级 UI 约定（`columnDef.meta` 的本地类型；不 import 传递依赖 table-core） */
export type ColumnUiMeta = {
  /** `th` 附加类：列宽（`w-[24%]`）· 对齐（`text-right`） */
  headClassName?: string;
  /** `td` 附加类：对齐 · `whitespace-normal` · `text-muted-foreground` */
  cellClassName?: string;
  /** 该列可点排序（缺省 false） */
  sortable?: boolean;
  /** 该列**固有方向**（`sorting.dir` 缺省时用于图标与 `aria-sort` 真值）· 缺省 `desc` */
  naturalDir?: 'asc' | 'desc';
  /** 该列的排序**档位**（服务端白名单值）；缺省取列 `id`（见 §2.4） */
  sortKey?: string;
  /** 该列是否参与列开关（§2.8）；缺省 `true`。保护列写 `false`（门户名称列） */
  hidable?: boolean;
};
```

| meta 键 | 落点 | 定值例（门户） |
|---------|------|----------------|
| `headClassName` | `th` | `w-[22%]` · `w-[8%] text-right` |
| `cellClassName` | `td` | `whitespace-normal text-muted-foreground` · `text-right` |
| `sortable` | `th`（渲染排序钮 + `aria-sort`） | 下载 / 收藏 / 更新 = `true`；**描述 · 名称 · 作者 = 不写**（后两者随 D0-8 下线 —— **v1.1 订正**） |
| `naturalDir` | 同列图标与 `aria-sort` 真值 | 下载 / 收藏 / 更新 = `desc`（**v1.1：仅三档用**） |
| `sortKey` | 排序回调携带的档位 | 更新列 = `newest`（列名 ≠ 档名，见 §5 D5） |
| `hidable` | 该列是否参与列开关（§2.8） | 门户名称列 = `false`（保护列）；其余缺省 `true`。**v1.3 注（E7）**：门户**本轮不消费列开关** ⇒ 该属性是**后续「门户列开关」笔的预留**，此处**显式承认它是一处预置**（用户拍「乙」），不当作已消费能力 |

### 2.5 密度契约

| 档 | 单元格 | 表头 | 行高 | 用途 |
|----|--------|------|------|------|
| `default` | 官方 `p-2`（**零覆盖**） | 官方 `h-10`=40（**零覆盖**） | 官方默认 | 控制台三页（主 design §10.1 已落值 **40**） |
| `comfortable` | 纵向覆写 `py-4`（横向仍官方 `px-2`） | 同官方（**不覆盖**） | ≈55（单行描述）· 3 行更高 | 门户（拍板 P5「宽行距」） |

**纪律**：`comfortable` **只动纵向**（`py-4`），不动横向、不动表头高、不动字阶 —— 控制台与门户的差异因此只剩「行距」一项（外加列宽与排序，见 §3.3）。

### 2.6 三态与载态两形态

| 态 | 形态 | 定值 |
|----|------|------|
| 载（`replace`） | 整表替换为骨架 | `SkeletonLoader variant="table" rows={skeletonRows} columns={列数}` —— **列数 = 可见列数**（**Q3 裁定**：按 `columnVisibility` 过滤后计数；若用 `columns.length`（现状），用户关掉列后载态又把该列冒出来 ⇒ **布局跳动**） |
| 载（`keepHeader`） | 保留表头 + N 行骨架 | 表头与真表**同形**（含排序钮）；每行 1 个 `TableCell colSpan={列数 + (rowActions ? 1 : 0)}`（**列数 = 可见列数** —— Q3 裁定 · 与 `replace` 行同口径 · 见 §2.8 V7）· 内容 = `Skeleton h-5 w-full rounded-md`；骨架行同样吃 `density` |
| 空 | 官方 `Empty`（`className="py-10"`） | `emptyMessage` ⇒ `EmptyDescription`（现状） |
| 错 | `ErrorState`（官方 `Alert` + 重试） | `error` / `onRetry`（现状） |

**有意差异（登记）**：现状门户载态表头是**纯文本**（因为没传排序回调，免第二套骨架件）；统一后 `keepHeader` 表头**与真表同形**（含排序钮，可点）。理由：排序是 URL 驱动，载态点击只是改写 URL，无竞态；且消除「同一件两态」的隐式分叉。若你否决，退路 = preset 在载态不传 `sorting`（1 行）。

### 2.7 无障碍与零覆盖纪律

- 排序钮：`<button>`（官方 `Button`）在 `th` 内；`th[aria-sort]` 表达状态；图标 `aria-hidden`；排序钮文案 = 列名（可读）
- 操作列：`rowActionsLabel` 必传（`sr-only` 兜底）；门户传 `rowActionsHeader`（可见）
- 单元格内**不嵌套可交互件**（下载 / 收藏为纯展示 `span`）
- 件内 `className` 的**唯一**外观写入 = `density` 的 `py-4`（门户档）；其余一律官方默认（表头高 / 底纹 / 边框 / 字阶全不覆盖）

### D1 「描述 3 行」依赖列宽可控 —— 三解法

**冲突**：3 行截断今天 = `table-fixed` **且** 描述列定宽 **且** `whitespace-normal` **且** `line-clamp-3`，四条同时成立。

去掉列宽控制后的**真实行为**（2026-09-21 真浏览器实测，见下方证据表）：(a) 表格被撑到 **913px**（容器 691 ⇒ **溢出 222px**，外层 `overflow-x-auto` 出横向滚动条）；(b) 名称列被长名撑到 **600px**，`truncate` **失效**（无界宽）；(c) 描述列被**极限压缩到 55px**（≈每行 2~3 字），`line-clamp` 仍触发但内容**不可读**。

> ✏️ **事实订正（v1.1 探针）**：旧表述「auto 布局下 3 行**不触发**」**不成立** —— 实测 3 行照样触发，问题是描述列被压死（55px）。

| 方案 | 做法 | 代价 / 风险 |
|------|------|-------------|
| **A ✅ 裁定（v1.2）** | 门户侧**保留**列宽控制，但只作**门户 preset 的本地布局**（`table-fixed` + 列宽类走 `meta.headClassName`）；统一件**不新增**「固定列宽能力」，只开一个 `tableClassName` **布局透传口** | 统一件 +1 prop；纪律须写明「该口只准放布局类，不得借它写观感类（色 / 尺寸）」；控制台零影响 |
| B | 彻底 auto 布局 ⇒ 语义降级为「描述最多 3 行（**能截才截**）」 | 与拍板 P5 自相矛盾（P5 的「宽行距」理由是「描述 3 行」）；长描述表格横向溢出；须改 `G20-4b` 断言口径 + 重新观感确认 |
| C | 只给描述列一个 `max-w`（名称列不设） | **已实证淘汰（v1.2 探针）**：`td` 的 `max-width` 在 auto 布局下**零效果**（C 与 B 逐项同值）—— 见下方证据表 |

**实测证据（2026-09-21 · 真浏览器 · 容器 691px · 超长描述 + 无空格长名 · 探针件见 §6.2）**：

| 方案 | 表格宽 | 溢出容器 | 描述列宽 | 名称列宽 | `truncate` | 描述 3 行 | 行高 |
|------|:---:|:---:|:---:|:---:|:---:|:---:|:---:|
| **B** 彻底 auto | 913 | **是（+222px）** | **55px** | 600px | **失效** | 触发但不可读 | 93 |
| **C** auto + 描述列 `max-width:200px` | 913 | **是（+222px）** | **55px** | 600px | **失效** | 触发但不可读 | 93 |
| **现状** `table-fixed` + 百分比列宽 | **691** | **否** | 156px | 145px | **生效** | **正常** | 93 |

- ⇒ **C 与 B 逐项同值** ⇒ 描述列上的 `max-width` **零效果** ⇒ **C 已实证淘汰**（v1.1 前为「预期」，现为实证）
